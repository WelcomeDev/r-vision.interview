# Задача: мастер создания задачи на сканирование

## Контекст

Вы дорабатываете консоль управления сканированием активов. Нужен мастер (wizard) из двух шагов, который собирает параметры задачи и отправляет её на бэкенд.

Верстка, стили и базовые компоненты уже готовы — их писать не нужно. Ваша работа — состояние формы, валидация, навигация между шагами и обработка ответа бэкенда.

## Шаги Wizard-формы

### Шаг 1. Основное

| Поле | Контрол | Правила                                                                                                                                                                       |
| --- | --- |-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Название задачи | `TextInput` | обязательное; 3–60 символов; буквы, цифры, пробел, дефис; уникальность проверяется на бэкенде через `useLazyCheckJobNameQuery` при потере фокуса, на время запроса в поле — индикатор загрузки (`loading` у `TextInput`); занятые имена: `Nightly scan`, `Аудит DMZ`, `Weekly vuln scan` |
| Тип сканирования | `Select` (`useGetScanTypesQuery`) | обязательный                                                                                                                                                                  |
| Профиль | `Select` (`useGetProfilesQuery`) | обязательный; **список зависит от типа**, грузится асинхронно; заблокирован, пока тип не выбран; при смене типа значение сбрасывается                                         |
| Теги | `MultiSelect` (`useGetTagsQuery`) | необязательные, не более 5                                                                                                                                                    |

### Шаг 2. Область сканирования

- Таблица активов: `useGetAssetsQuery({ search, groupId })`.
- Поиск по хосту/IP (с debounce) и фильтр по группе (`useGetAssetGroupsQuery`).
- Нужно выбрать **минимум один** актив.
- Для каждого выбранного актива — обязательная строка портов, редактируется прямо в таблице
  (`TableCellInput`). Формат: числа `1..65535` и/или диапазоны через запятую, например
  `22,80,443` или `1000-2000,8080`. Некорректная строка — ошибка в ячейке и подсветка строки
  (`isRowInvalid`).
- Выбор и введённые порты не должны теряться при смене поиска/фильтра — даже если актив
  пропал из текущей выдачи.

Это последний шаг, здесь же кнопка «Создать задачу»:

- Отправка через `useCreateScanJobMutation`.
- Бэкенд валидирует повторно и может вернуть 422: у ошибки есть `fieldErrors`, ключи — пути
  полей (`general.name`, `general.profileId`). Нужно показать общий `Alert`, разложить ошибки
  по полям и вернуть пользователя на шаг с первой ошибкой, пометив этот шаг в `Stepper`.
- Воспроизвести 422 можно так: название, содержащее `demo`; либо профиль «Полный набор
  проверок» вместе с активом критичности `critical`.
- Успех — экран с id созданной задачи.

## Общие требования

1. Валидация клиентская. Поле проверяется по `onBlur`; после того как ошибка показана, поле
   перепроверяется на вводе. Кнопка «Далее» валидирует шаг целиком, блокировать её не нужно —
   показывайте ошибки.
2. Введённые данные не теряются при переходах назад и вперёд.
3. По `Stepper` можно вернуться на пройденный шаг кликом; перепрыгнуть вперёд через
   невалидный шаг нельзя; шаг с ошибками помечается.
4. Задача создаётся только по явному нажатию «Создать задачу»: Enter в поле и повторный клик
   по «Далее» не должны её отправлять.
5. Состояния загрузки и ошибок сети видны пользователю: `isLoading` / `isFetching` / `error`
   из хуков RTK Query, `Select`, `MultiSelect`, `DataTable` и `Button` умеют `loading`.
   Запрос, для которого ещё нет аргумента, не должен уходить (`skipToken`).

## Порядок реализации

Идём этапами: каждый следующий начинаем, когда предыдущий работает. Успеть всё не обязательно —
важно, чтобы то, что сделано, работало.

1. **Шаг 1: поля и валидация** 
   1. Название 
   2. тип сканирования
   3. профиль 
   4. теги. 
   5. Связка `тип сканирования` → `профиль сканирования`: 
      1. список профилей грузится по выбранному типу, 
      2. без типа запрос не уходит, 
      3. при смене типа выбранный профиль сбрасывается
2. **Шаг 2: таблица**:
   1. Загрузка активов 
   2. фильтр по группе и поиск с debounce 
      1. готового `useDebounce` в проекте нет. Его нужно написать самому
   3. Выбор строк, поля портов прямо в ячейках с проверкой формата. Выбор и введённые порты не теряются при смене фильтров.
3. **Отправка в консоль.** Собрать payload (`assetIds` + `ports` → `targets`) и вывести его через `console.log`
4. **Проверка имени на уникальность.** `useLazyCheckJobNameQuery` по blur поля названия:
   1. ошибка видна сразу после потери фокуса, 
   2. на время запроса в поле крутится индикатор. 
   3. Клиентские правила проверяем первыми — незачем спрашивать бэкенд про заведомо плохое имя.
---
Усложнения:
1. **Реальная отправка и ошибки бэкенда.** 
   1. `useCreateScanJobMutation`, экран успеха и разбор 422: 
   2. разложить `fieldErrors` по полям, вернуть пользователя на шаг с первой ошибкой и пометить этот шаг в `Stepper`. Проверяется на названии, содержащем `demo`.
2. **Последний сценарий 422.** Профиль «Полный набор проверок» вместе с активом критичности `critical` — правило живёт на бэкенде, ошибка приходит по полю `general.profileId`.

## Definition of Done

**MVP (на него ориентируемся по времени):** этапы 1–3 — оба шага с валидацией, навигация,
сохранение данных при возврате и собранный payload в консоли.

**Дальше по времени:** этапы 4–6, а если останется время — фокус на первом невалидном поле
и обработка сетевых ошибок при загрузке справочников.
