# Задача: мастер создания задачи на сканирование

## Контекст

Вы дорабатываете консоль управления сканированием активов. Нужен мастер (wizard) из двух
шагов, который собирает параметры задачи и отправляет её на бэкенд.

Верстка, стили и базовые компоненты уже готовы — их писать не нужно. Ваша работа — состояние
формы, валидация, навигация между шагами и обработка ответа бэкенда.

## Что уже есть

| Что | Где | Комментарий |
| --- | --- | --- |
| Компоненты | `src/components` | `TextField`, `SelectField`, `MultiSelectField` — Field + контрол одной строкой; отдельные `Field`, `TextInput`, `Select`, `MultiSelect` — для ручной сборки; плюс `DataTable`, `TableCellInput`, `Stepper`, `Checkbox`, `Button`, `Alert` |
| Витрина компонентов | вкладка «Компоненты» в приложении | живой пример пропсов каждого компонента |
| Данные | `src/api/scanApi.ts` | RTK Query поверх мок-бэкенда: `useGetScanTypesQuery`, `useGetProfilesQuery`, `useGetTagsQuery`, `useGetAssetGroupsQuery`, `useGetAssetsQuery`, `useLazyCheckJobNameQuery`, `useCreateScanJobMutation` |
| Мок-бэкенд | `src/api/mockApi.ts` | промисы с задержкой и ошибками; store уже подключён в `main.tsx` |
| Модель формы и шаги | `src/task/formModel.ts` | стартовая точка, менять можно |
| Точка входа | `src/task/ScanJobWizard.tsx` | тут вы и пишете |

Все контролы управляемые: `value` + `onChange` + `invalid`. `TextField` / `SelectField` /
`MultiSelectField` — это уже собранные `Field` + контрол: принимают `label`, `required`, `hint`,
`error` и пропсы контрола одним списком. Если нужна нестандартная разметка, те же кирпичики
собираются вручную через `Field` с render-prop.

В зависимостях уже стоят `react-hook-form`, `yup`, `@hookform/resolvers`, `@reduxjs/toolkit`. Можно обойтись
`useState` — важно уметь объяснить выбор.

## Шаги Wizard-формы

### Шаг 1. Основное

| Поле | Контрол | Правила                                                                                                                                                                       |
| --- | --- |-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Название задачи | `TextInput` | обязательное; 3–60 символов; буквы, цифры, пробел, дефис; уникальность проверяется через `useLazyCheckJobNameQuery` (занято: `Nightly scan`, `Аудит DMZ`, `Weekly vuln scan`) |
| Тип сканирования | `Select` (`useGetScanTypesQuery`) | обязательный                                                                                                                                                                  |
| Профиль | `Select` (`useGetProfilesQuery`) | обязательный; **список зависит от типа**, грузится асинхронно; заблокирован, пока тип не выбран; при смене типа значение сбрасывается                                         |
| Теги | `MultiSelect` (`useGetTagsQuery`) | необязательные, не более 5                                                                                                                                                    |

### Шаг 2. Область сканирования

- Таблица активов: `useGetAssetsQuery({ search, groupId })`.
- Поиск по хосту/IP (с debounce) и фильтр по группе (`useGetAssetGroupsQuery`).
- Нужно выбрать **минимум один** актив.
- Для каждого выбранного актива — обязательная строка портов, редактируется прямо в таблице
  (`TableCellInput`). Формат: числа `1..65535` и/или диапазоны через запятую, например
  `22,80,443` или `1000-2000,8080`. Некорректная строка — ошибка в ячейке и подсветка строки
  (`isRowInvalid`).
- Выбор и введённые порты не должны теряться при смене поиска/фильтра — даже если актив
  пропал из текущей выдачи.

Это последний шаг, здесь же кнопка «Создать задачу»:

- Отправка через `useCreateScanJobMutation`.
- Бэкенд валидирует повторно и может вернуть 422: у ошибки есть `fieldErrors`, ключи — пути
  полей (`general.name`, `general.profileId`). Нужно показать общий `Alert`, разложить ошибки
  по полям и вернуть пользователя на шаг с первой ошибкой, пометив этот шаг в `Stepper`.
- Воспроизвести 422 можно так: название, содержащее `demo`; либо профиль «Полный набор
  проверок» вместе с активом критичности `critical`.
- Успех — экран с id созданной задачи.

## Общие требования

1. Валидация клиентская. Поле проверяется по `onBlur`; после того как ошибка показана, поле
   перепроверяется на вводе. Кнопка «Далее» валидирует шаг целиком, блокировать её не нужно —
   показывайте ошибки.
2. Введённые данные не теряются при переходах назад и вперёд.
3. По `Stepper` можно вернуться на пройденный шаг кликом; перепрыгнуть вперёд через
   невалидный шаг нельзя; шаг с ошибками помечается.
4. Задача создаётся только по явному нажатию «Создать задачу»: Enter в поле и повторный клик
   по «Далее» не должны её отправлять.
5. Состояния загрузки и ошибок сети видны пользователю: `isLoading` / `isFetching` / `error`
   из хуков RTK Query, `Select`, `MultiSelect`, `DataTable` и `Button` умеют `loading`.
   Запрос, для которого ещё нет аргумента, не должен уходить (`skipToken`).

## Порядок реализации

Идём этапами: каждый следующий начинаем, когда предыдущий работает. Успеть всё не обязательно —
важно, чтобы то, что сделано, работало.

1. **Шаг 1: поля и валидация.** Название, тип сканирования, профиль, теги. Связка
   тип → профиль: список профилей грузится по выбранному типу, без типа запрос не уходит,
   при смене типа выбранный профиль сбрасывается. Валидация по `onBlur`.
2. **Шаг 2: таблица.** Загрузка активов, поиск с debounce и фильтр по группе, выбор строк,
   поля портов прямо в ячейках с проверкой формата. Выбор и введённые порты не теряются при
   смене фильтров.
3. **Отправка в консоль.** Собрать payload (`assetIds` + `ports` → `targets`) и вывести его
   через `console.log`. Здесь же навигация: `Stepper`, «Назад» без потери данных, защита от
   случайной отправки.
4. **Проверка имени на уникальность.** `useLazyCheckJobNameQuery` на переходе со шага 1.
5. **Реальная отправка и ошибки бэкенда.** `useCreateScanJobMutation`, экран успеха и разбор
   422: разложить `fieldErrors` по полям, вернуть пользователя на шаг с первой ошибкой и
   пометить этот шаг в `Stepper`. Проверяется на названии, содержащем `demo`.
6. **Последний сценарий 422.** Профиль «Полный набор проверок» вместе с активом критичности
   `critical` — ошибка приходит по полю `general.profileId`.

## Definition of Done

**MVP (на него ориентируемся по времени):** этапы 1–3 — оба шага с валидацией, навигация,
сохранение данных при возврате и собранный payload в консоли.

**Дальше по времени:** этапы 4–6, а если останется время — фокус на первом невалидном поле
и обработка сетевых ошибок при загрузке справочников.

## Что делать не нужно

Стили и адаптив, тесты, роутинг, i18n, свои UI-компоненты, оптимизацию ре-рендеров ради
оптимизации. Мы смотрим на структуру состояния и работу с валидацией.

## Ориентир по времени (45–60 минут)

| Время | Что |
| --- | --- |
| 0–5 | Осмотреться: витрина компонентов, `api`, `formModel` |
| 5–10 | Проговорить, как будете хранить состояние и валидировать шаги |
| 10–25 | Шаг 1 |
| 25–45 | Шаг 2 (таблица + порты) и отправка формы |
| 45–60 | Обсуждение решения |

Думать вслух — часть задачи. Гуглить документацию можно.
